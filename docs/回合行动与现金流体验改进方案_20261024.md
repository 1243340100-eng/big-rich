# 回合行动与现金流体验改进方案

- 日期：2026-10-24
- 状态：已按推荐路线实施 P0–P3；具体取舍和验证见 [实施记录](./回合行动与现金流实施记录_20261024.md)
- 目标：把“买地 → 升级 → 收租 → 结算”做成一条清晰的主循环，减少玩家在多个面板之间找按钮和临时筹钱
- 依据：本方案根据当前 [App.tsx](../src/App.tsx)、[engine.ts](../server/engine.ts)、[finance.ts](../shared/finance.ts) 的实际规则整理

## 1. 一句话总结

当前游戏已经有完整功能，但**行动入口太分散，关键结果需要玩家自己计算，现金变负后缺少清晰的补救路径**。

下一轮体验改造应围绕三件事：

1. 底部只保留一个“当前最该做的事”主按钮，其他操作收进“更多操作”。
2. 把利息、税、维护、现金跑道和补现金方案集中到现金流仪表盘。
3. 买入后直接进入“立即升级”的上下文，让买地、升级、收租形成连续反馈。

---

## 2. 当前基线

### 2.1 已有能力

- 右侧抽屉已有总览、地产、股票、银行、交易五个入口。
- 底部已有回合面板，包含掷骰、买入、公开拍卖、结束回合、补现金等零散按钮。
- 地产卡片和右侧抽屉已有升级、抵押、赎回、出售。
- 已有现金为负检测和“申请破产重组”按钮。
- 已有完整建筑升级施工动画和 `UpgradeableBuilding`。
- 已有股票、银行、地产三类可快速变现资产。

### 2.2 当前问题

| 问题 | 当前表现 |
| --- | --- |
| 主行动不唯一 | 回合面板、右侧五个标签、地块弹窗、拍卖面板各自有按钮 |
| 买入信息不足 | 只显示价格，不显示买后现金、租金、维护和税费变化 |
| 管理阶段被拆散 | 买入后要打开“地产”标签才能升级 |
| 现金为负后路径不清晰 | 玩家需要自己判断取存款、卖股票、抵押、贷款还是重组 |
| 固定支出不透明 | 利息、税、维护只在日志中出现，玩家难以预估下一回合 |
| 结算反馈弱 | 买入、升级、收租和结算缺少统一、可感知的反馈 |
| 移动端更明显 | 主按钮、骰子、补现金和抽屉操作分散在不同区域 |

## 3. 方案一：底部行动条 + 唯一主 CTA

### 3.1 设计原则

1. **同一时刻只出现一个视觉上的主按钮。**
2. 主按钮必须对应“当前阶段最应该做的下一步”。
3. 破坏性操作永远不是主按钮。
4. 主按钮上直接显示结果预览，而不是只写动作名。
5. 右侧抽屉保留，但降级为“查看详情 / 更多操作”，不再承担主流程导航。
6. 所有按钮必须有禁用原因，不能只变灰。

### 3.2 阶段与主按钮映射

| 游戏状态 | 主按钮 | 次按钮 | 说明 |
| --- | --- | --- | --- |
| 等待开局，房主 | 开始对局 | 加 AI、房间设置 | 至少 2 人才能开始 |
| 等待开局，非房主 | 等待房主开局 | 无 | 不放置不可用假按钮 |
| 别人的回合 | 等待对方行动 | 更多操作 | 可以做股票、银行等离回合操作 |
| 轮到我，掷骰阶段 | 掷骰子 | 捷径（如位置允许） | 显示捷径费用 |
| 轮到我，买到无主地 | 买入 X 万 | 放弃并拍卖 | 必须展示买后现金和租金 |
| 拍卖进行中 | 参与竞拍 / 出价 | 放弃本轮 | 显示当前最高价和剩余时间 |
| 轮到我，管理阶段，选中可升级地产 | 立即升级 X 万 | 结束回合 | 升级是当前上下文的首选 |
| 轮到我，管理阶段，未选中地产 | 结束回合 | 管理地产 | 打开地产列表 |
| 轮到我，管理阶段，选中已满级/抵押地产 | 结束回合 | 查看地产 | 升级按钮禁用并说明原因 |
| 现金为负 | 补现金 | 结束回合（禁用） | 主按钮打开急救面板 |
| 对局结束 | 查看排名 | 返回首页 | 当前已有逻辑 |

> 关键取舍：管理阶段不能固定把“结束回合”做成唯一主按钮，否则会弱化升级。  
> 推荐做法是：**有选中且可升级的地产时，主按钮升级；没有上下文时，主按钮结束回合。**  
> 地块弹窗中的“立即升级”只作为同一动作的上下文快捷入口，不再放一个同等分量的主按钮。

### 3.3 CTA 上直接显示结果预览

| 动作 | 第一行 | 第二行 |
| --- | --- | --- |
| 买入 | 买入 87 万 | 租金 11.2 万/次 · 买后现金 113 万 |
| 升级 | 升级 32 万 | 租金 8.4 → 11.2 万/次 · 升级后现金 81 万 |
| 结束回合 | 结束回合 | 下回合开始预计支出 6.8 万 |
| 补现金 | 补现金 18 万 | 现金 -18 万 → 0 万以上 |
| 掷骰 | 掷骰子 | 单骰 · 移动 1–6 格 |
| 放弃并拍卖 | 放弃并拍卖 | 其他玩家可竞价 |

**文案修正：**

- 租金是“其他玩家落到该地产时支付一次”，不是每回合固定收入。  
  建议统一使用“**万/次**”，不要写成“万/回合”，避免误导。
- 升级预览中的租金基于当前经济周期和地产等级计算，应标注“当前经济周期下”。
- 买入预览中的现金 = 当前现金 - 成交价格。
- 升级预览还应提示维护费变化：每级维护增加约 `0.6 万/回合`（企业家为 `0.48`）。

### 3.4 更多操作

“更多操作”打开一个轻量底部菜单或抽屉入口，包含：

- 玩家与城市概况
- 地产
- 股票
- 银行
- 交易
- 城市会客厅
- 游戏指南

右侧抽屉里的五个标签可以暂时保留作为进阶入口，但主流程不再依赖玩家先理解这些标签。

### 3.5 与其他入口的同步

- 买入、升级、结束回合只能通过统一的 action 函数执行，避免三个面板各写一套逻辑。
- 买入成功后自动选中刚买的地块，底部 CTA、地块弹窗和右侧地产数据同步更新。
- 拍卖进行时，底部主按钮只负责打开拍卖操作，不在主按钮和抽屉里同时放两个竞价输入框。
- 现金为负时，其他“结束回合”“买入”类按钮统一禁用，主按钮变为“补现金”。

## 4. 方案二：现金流仪表盘与补现金急救

### 4.1 仪表盘放在哪里

建议常驻在回合面板内，默认只显示一行摘要，点击后展开：

```text
现金 42 万 · 固定支出/回合 6.8 万 · 约可撑 6 回合
[查看现金流]
```

展开后显示：

- 当前现金
- 存款
- 可快速变现的股票市值
- 可抵押额度
- 可用信用贷款额度
- 本回合已结算的利息 / 税 / 维护
- 下回合预计固定支出
- 现金跑道
- 现金缺口（如果为负）

### 4.2 计算口径

当前 `beginTurn` 在每位玩家回合开始时扣除：

| 项目 | 公式 |
| --- | --- |
| 信用贷款利息 | `debt × loanRate` |
| 抵押贷款利息 | `Σ 抵押金额 × (baseRate + 2%)` |
| 地产税 | `Σ 地产估值 × 0.8% + max(0, Σ 地产估值 - 500) × 1%` |
| 维护费 | `Σ 地产等级 × 0.6 × 职业系数` |
| 存款利息收入 | `deposit × 1%` |

因此：

```text
下回合固定支出 = 信用贷款利息 + 抵押贷款利息 + 地产税 + 维护费
现金跑道 = 固定支出 > 0 ? floor(现金 / 固定支出) : ∞
```

必须标注：

> **仅按当前债务、地产和经济周期估算，不含工资、租金、股息、股票波动、事件和后续操作。**

不能把“跑道”写成精确预测。租金不是每回合必得，工资也不一定每回合触发。

### 4.3 本回合实际结算明细

当前服务端只保存 `lastFlow` 汇总，没有保留 `interest / tax / upkeep` 的分项。

建议：

- **第一阶段（不改服务端）**：显示“下回合预计固定支出”，并展示 `lastFlow` 汇总。
- **第二阶段（建议）**：在 `Player` 上增加可选字段：

```ts
lastSettlement?: {
  interest: number;
  tax: number;
  upkeep: number;
  depositIncome: number;
  total: number;
};
```

由 `beginTurn` 写入，存档迁移时默认缺省。这样仪表盘可以显示真实的“本回合利息 / 税 / 维护”，而不是客户端估算。

### 4.4 现金为负时的急救面板

触发条件：

- 现金小于 0；或
- 当前现金足够但下回合预计结算后会小于 0。

面板按“净代价从低到高”动态排序，而不是固定写死：

| 顺序 | 手段 | 收益 | 代价 | 默认建议 |
| --- | --- | --- | --- | --- |
| 1 | 取存款 | 存款金额 | 损失后续 1% 存款增长 | 优先 |
| 2 | 卖股票 | 扣费、税、滑点后的净额 | 手续费、资本利得税、改变持仓 | 视情况 |
| 3 | 申请信用贷款 | 可用额度内现金 | 利息、信用占用 | 低利率时优先 |
| 4 | 抵押地产 | 估值的 60% | 失去租金、后续赎回 5% 手续费、抵押利息 | 中 |
| 5 | 出售地产 | 估值 70% - 抵押债务 | 永久失去资产和未来租金 | 尽量避免 |
| 6 | 破产重组 | 30 万重启金、减免债务 | 失去地产、股票、存款，信用降 D | 最后手段 |

> 对原提案的补充：原列表没有“出售地产”，但当前服务端已有 `sellProperty`，急救路径应包含它。  
> 贷款和抵押的先后不应固定：信用利率低时贷款更便宜；抵押会失去租金，实际代价可能更高。  
> 因此要按当前利率、租金损失、手续费和税费**动态排序**。

每一行必须显示：

- 操作后现金
- 是否补足
- 代价说明
- 是否影响后续收租/信用/资产
- 需要二次确认的破坏性操作

### 4.5 “一键补足”的正确交互

不建议让“一键补足”静默替玩家做决定。建议采用：

```text
现金缺口：18 万
建议方案：
  取存款 10 万 → 现金 -8 万
  卖出星海银行 200 股 → 现金 0.6 万
  申请贷款 3 万 → 现金 3.6 万
[调整方案] [确认执行]
```

原则：

1. 默认展示推荐方案，但用户可以取消其中任何一步。
2. 确认前显示每一步执行后的现金。
3. 破产重组永远不自动加入方案，必须单独确认。
4. 执行完成后必须重新显示现金，不自动结束回合。
5. 拍卖期间、非本人回合等状态要禁用对应操作并说明原因。

**实施注意：**

- 当前服务端一次只接受一个 action。真正的一次确认执行多步，需要新增服务端“救援计划”动作或批量接口，并做原子校验。
- 第一阶段建议只做“建议下一步”，玩家逐项确认；不要用前端连续 `emit` 模拟多步，否则价格或状态变化时可能部分成功、部分失败。
- 若要做真正的一键补足，服务端应按顺序重新校验每一步，任何一步失败则整体不执行。

### 4.6 现金跑道的边界

- 现金为负：显示缺口，不显示“还能撑 0 回合”作为唯一信息。
- 固定支出为 0：显示“暂无固定支出”。
- 有拍卖保证金：计算可用现金时要考虑预留资金。
- 有交易提案/拍卖进行中：禁用会破坏交易或拍卖的急救操作。
- 现金足够但不足一个完整回合：显示“不足 1 回合”，不要四舍五入成 0。

## 5. 方案三：买地、升级、收租连成一套动作

### 5.1 买入后的自动上下文

当前买入后服务端把阶段切到 `manage`，但没有把“刚买的地块”作为 UI 上下文。

建议：

1. 玩家点击买入时，前端记住 `pendingTile`。
2. 收到新状态后，如果该地块已经属于自己，自动选中并打开地块弹窗。
3. 底部 CTA 同步变为“立即升级 X 万”，次要按钮为“结束回合”。
4. 如果升级费用不足，升级按钮禁用并提示“现金不足，可先结束回合或补现金”。

这样不需要改服务端字段，也不依赖“购买成功”回执。

### 5.2 地块弹窗的升级区

```text
银杏公寓 · Lv.1
当前租金：8.4 万/次
升级费用：32 万
升级后租金：11.2 万/次
升级后现金：81 万
维护：+0.6 万/回合

[立即升级 32 万]   [管理资产]
```

规则约束：

- 只有管理阶段、地产所有者、当前回合可以升级。
- 已抵押或 Lv.3 时禁用并显示原因。
- 升级后立即更新等级、估值、租金、现金和维护预览。
- Lv.3 后按钮改为“已满级”，不留下无效主按钮。
- 不自动结束回合，玩家可以继续升级其他地产。
- 地产税会随估值上升而增加，升级预览可提示“下回合固定支出将增加”，具体金额交给现金流仪表盘。

### 5.3 升级后的反馈

继续复用现有 `UpgradeableBuilding` 施工动画：

- 脚手架逐层升起
- 围挡落下
- 建筑揭幕
- 屋顶加层
- 金色粒子和落成脉冲

在此基础上补充：

- 地块弹窗中的“租金 X → Y”数字变化
- 屏幕上的浮字：`租金 +2.8 万/次`
- 现金数字短暂滚动到新值
- 升级完成后的轻量提示，不阻塞下一步

### 5.4 音效与动画

建议把反馈分成两层：

| 场景 | 动画 | 音效 |
| --- | --- | --- |
| 买入成功 | 地契/卡片章节翻页，现金数字滚动 | 印章或硬币声 |
| 升级 | 现有 4.15 秒施工动画 + 金币浮字 | 施工、锤击、落成声 |
| 收租 | 租金数字跳动，所有权方向高亮 | 收银/金币声 |
| 回合结算 | 利息、税、维护逐项滚出，最后显示净变化 | 盖章/合上账本声 |
| 破产重组 | 红色警示 + 资产清单收拢 | 低沉确认声，不使用庆祝音效 |

实现原则：

- 音频必须在用户手势后初始化，不能自动播放。
- 提供独立静音开关，不能把“减少动态效果”当作静音。
- 动画不能阻塞服务端已经确认的状态。
- 连续操作时限制音效叠加，避免刺耳。
- 没有合适的授权音频时，宁可不做，不引入来源不明的素材。

### 5.5 “结账”的时机需要澄清

当前服务端的利息、税、维护在**每位玩家回合开始时**自动扣除，不是玩家点“结束回合”时扣。

因此“结账动画”有两个可选方案：

- **方案 A（推荐）**：回合开始时播放一张“本回合结算回执”，显示利息、税、维护、存款利息和净变化；结束回合时只做轻量的“账本合上”过渡。
- **方案 B**：改变扣费时机到结束回合，但这会影响规则、AI 和测试，不建议为了动画改财务时序。

如果只做买入/升级的交易反馈，不改财务时序，成本最低。

## 6. 实施顺序

### P0：主流程收口，不改服务端

1. 抽出统一的状态到 CTA 映射，保证任何阶段只有一个主按钮。
2. 主按钮加入买入、升级、结束回合的结果预览。
3. 买入后自动选中地块，地块弹窗加入“立即升级”。
4. 现金为负时主按钮改为“补现金”，其他动作禁用。

验收重点：玩家不打开右侧五个标签，也能完整完成一个回合。

### P1：现金流仪表盘与急救

1. 新增纯函数计算下回合固定支出、现金跑道和快速变现额度。
2. 回合面板增加现金流摘要与展开面板。
3. 现金为负时提供按代价排序的急救列表。
4. 第一阶段只做逐项操作，不做静默批量执行。

### P2：结算明细与一键补足

1. 服务端新增结构化结算明细 `lastSettlement`。
2. 回合开始显示逐项结账回执。
3. 如确有必要，再新增服务端原子救援动作，支持一次确认执行多步。

### P3：反馈与音效

1. 买入、升级、收租的浮字和数字滚动。
2. 施工、金币、结账音效。
3. 静音设置、音量、低端设备降级策略。

| 财务公式 | [finance.ts](../shared/finance.ts) |
| 测试 | `tests/` 下新增现金流、CTA 状态和救援排序测试 |

建议不要把这些逻辑散落在多个 JSX 条件里，而是先建立：

```ts
type PrimaryAction =
  | { kind: 'roll' }
  | { kind: 'buy'; tileId: number; cost: number; rent: number; cashAfter: number }
  | { kind: 'upgrade'; tileId: number; cost: number; rentBefore: number; rentAfter: number }
  | { kind: 'end' }
  | { kind: 'rescue'; gap: number }
  | { kind: 'auction'; ... };
```

UI 只消费这个状态，避免以后加功能时又出现两个主按钮。

## 9. 需要确认的问题

1. 管理阶段的主按钮默认是“升级”还是“结束回合”？
   - 本方案建议：选中可升级地产时升级，否则结束回合。
2. “一键补足”是一次确认执行多步，还是第一阶段先做逐项确认？
   - 本方案建议先逐项确认；真正批量执行需要服务端原子接口。
3. 是否接受新增 `lastSettlement` 字段来展示真实的结算明细？
4. 音效是否作为下一轮必做项，还是先做视觉反馈、音效后置？
5. “结账动画”指买入/升级交易，还是回合开始的利息/税/维护结算？
   - 本方案建议后者放在回合开始，前者做交易反馈。
6. 右侧五个标签是保留为进阶入口，还是最终只保留“更多操作”入口？
   - 本方案建议先保留，但不再作为主流程。

## 10. 非目标

- 不自动替玩家卖股票、抵押或贷款。
- 不为了动画改变服务端财务时序。
- 不在未授权的情况下加入音频素材。
- 不删除右侧抽屉的查看能力。
- 不把股票、银行、交易等完整功能搬进回合面板。
- 不制造无法执行的假按钮。

## 11. 对原提案的关键修正

1. **租金单位不是“万/回合”**：租金是其他玩家落到地产时支付一次，文案应统一为“万/次”，否则会高估稳定收入。
2. **管理阶段不能固定只做一个主按钮**：选中可升级地产时以“升级”为主、结束回合为次；没有上下文时才以“结束回合”为主。
3. **补现金顺序不应写死**：贷款、抵押、卖股票的代价随利率、租金损失、手续费和税费变化，应按当前状态动态排序。
4. **“一键补足”不是前端连续点击**：真正一次确认执行多步，需要服务端原子校验；第一阶段应先做“建议下一步 + 逐项确认”。
5. **结账发生在回合开始**：利息、税、维护由 `beginTurn` 自动扣除，不是点“结束回合”时扣除；结账动画应放在回合开始，或明确改成交易反馈。
6. **升级反馈不能只做音效**：还要同步租金、现金、维护和地产税的变化，避免动画很爽但玩家不知道账变成了什么样。
